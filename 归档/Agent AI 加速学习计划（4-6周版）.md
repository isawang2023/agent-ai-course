## 第1周 · AI / LLM 是什么

> [!tip] 本周目标
> 听到研发说"这个模型 128K context，推理成本高"时，你能理解在说什么，并能反问"那用户输入通常多长？会不会超？"

### 先用起来

> [!example] 不看视频、不看文章，先用 · 约 1h
> 拿你工作中的真实任务去试：
> - [ ] 把一份会议纪要丢给 ChatGPT 或 Claude，让它提炼 3 个行动项
> - [ ] 让 AI 帮你写一段需求描述或邮件（先写提示词，改到满意为止）
> - [ ] 让 AI 做一件它不擅长的事（比如问最近的新闻），观察它会不会编造

### 对比实验

> [!example] 约 30min
> - [ ] 同一个问题，分别问 **ChatGPT / Claude / DeepSeek**，对比回答风格和质量
> - [ ] 把一篇 5000 字以上的文章塞给 AI，看它是否会遗漏前面的内容
> - [ ] 试试模糊指令 vs 清晰指令的差别（"帮我写个方案" vs "你是科研产品经理，请为'AI 论文总结'功能写需求文档，包含用户场景、核心功能、验收标准"）

### 推荐课程

> [!info] 选 1-2 个，比看视频更系统 · 约 2-6h
> - [ ] **AI for Everyone**（DeepLearning.AI，~6h，免费）— Andrew Ng 专为非技术人设计，78 万人学过
>   - [打开课程](https://www.deeplearning.ai/courses/ai-for-everyone/)
> - [ ] **Anthropic Academy — Claude 101**（~1-2h，免费，有证书）— 从零学会用 Claude
>   - [打开课程](https://anthropic.skilljar.com/)
> - [ ] **OpenAI Academy — AI Foundations**（免费）— OpenAI 官方入门，含练习和测评
>   - [打开课程](https://academy.openai.com/pages/courses)
> - [ ] **Karpathy — How I use LLMs**（YouTube）— 不讲原理，讲一个 AI 专家日常怎么用 AI
>   - 搜索 "Andrej Karpathy How I use LLMs"

### 术语卡

> [!quote] 搞懂这 5 个词
> | 概念 | 一句话解释 |
> | --- | --- |
> | Token | 模型读写的最小单位，大约 1 个中文字 = 1-2 token |
> | Context Window | 模型一次能看到的最大范围，超出就会"忘记" |
> | Embedding | 把文字变成数字向量，用来做搜索和相似度计算 |
> | Inference | 模型生成回答的过程 |
> | Temperature | 控制回答的随机程度，0=确定，1=发散 |

### 快速验收

> [!question]- 题目 · 点击展开
> 你要做一个"论文全文分析"功能，一篇论文 5 万字。研发说用 GPT-3.5（4K context）。
> **这个方案可行吗？为什么？**

> [!success]- 参考答案 · 点击展开
> **不可行。** 5 万字 ≈ 5-10 万 token，远超 4K 上限。
>
> 两个可行方案：
> 1. **换模型** — 用 GPT-4o（128K）或 Claude（200K），context 够大
> 2. **改架构** — 用 RAG，先把论文切片 + 向量化，检索相关段落再回答
>
> **产品视角的提醒：** 你应该主动追问研发"用哪个模型、context 多大"，而不是等做完才发现截断。

> [!warning] 常见坑
> - **别纠结题目里的数字。** GPT-3.5 / 4K 是 2023-24 的语境，2026 年主流模型 context 普遍 128K+。这题的价值是"先算 token 再谈方案"的思维，不在数字。
> - **别只问"能不能做"。** 一次调用多少钱、P95 延迟多少，往往比 context 上限更快决定方案生死。

## 第2周 · Agent 到底在干什么

> [!tip] 本周目标
> 能区分 Prompt（一次性指令）、Workflow（固定流程）、Agent（动态决策），并且拿到一个需求时能判断应该用哪个。

### 学习资料

> [!info] 必读博客，不是论文 · 约 1.5h
> - [ ] **Anthropic — Building Effective Agents**
>   - [打开文章](https://www.anthropic.com/engineering/building-effective-agents)
>   - 最重要的一篇。讲清楚 Workflow vs Agent、5 种架构模式（Prompt Chaining / Routing / Parallelization / Orchestrator / Multi-Agent）和适用场景。读完这篇你能参与 80% 的架构讨论
> - [ ] **Lilian Weng — LLM Powered Autonomous Agents**
>   - [打开文章](https://lilianweng.github.io/posts/2023-06-23-agent/)
>   - 配图多，讲清楚 Agent = Planning + Memory + Tool Use 三要素

### 动手练习

> [!example] 约 30min
> - [ ] 用 Claude 开启 tool use，给它一个任务（如"帮我搜索最近的 AI 新闻并总结"），观察它怎么"决定调工具 → 拿到结果 → 继续推理"，数一数它循环了几轮
> - [ ] 用 ChatGPT Code Interpreter 跑一个数据分析（上传一个 CSV），观察多步骤执行：读文件 → 生成代码 → 运行 → 看错误 → 修改代码

### 术语卡

> [!quote] 搞懂这 6 个词
> | 概念 | 一句话解释 |
> | --- | --- |
> | Agent Loop | 循环：思考 → 行动 → 观察结果 → 再思考，直到任务完成 |
> | ReAct | Reasoning + Acting，模型边想边做的模式 |
> | Workflow | 预定义的固定流程，人设计好步骤，模型执行 |
> | Agent | 模型自己决定下一步做什么，流程不固定 |
> | Orchestration | 多个 Agent 之间的协调和任务分配 |
> | Handoff | 一个 Agent 把任务交给另一个 Agent |

### 快速验收

> [!question]- 题目 · 点击展开
> 以下三个场景，分别用 Prompt / Workflow / Agent？
> 1. 把一段英文摘要翻译成中文
> 2. 用户输入论文题目 → 搜索文献 → 提取摘要 → 生成综述草稿（流程固定）
> 3. 用户说"帮我分析这份用户调研数据"，但你不知道数据什么格式、需要分析什么维度

> [!success]- 参考答案 · 点击展开
> 1. **Prompt** — 单次任务，一个指令搞定，不需要多步
> 2. **Workflow** — 多步骤但流程固定，每步输入输出明确，提前设计好
> 3. **Agent** — 不确定需要几步，每步做什么依赖上一步结果，需要模型自己决策
>
> **判断原则：流程能不能提前写死？能写死用 Workflow，不能写死才用 Agent。**

> [!warning] 常见坑
> - **别为了"看起来高级"上 Agent。** Agent 的代价是成本和延迟不可控，能用 Workflow 稳定解决的场景硬上 Agent，是产品决策上最常见的浪费。
> - **别把"多轮对话"当成 Agent。** 能聊天不等于会自主决策。

## 第3周 · MCP / RAG / Memory 这些工程概念

> [!tip] 本周目标
> 能用一句话分别解释 MCP、RAG、Memory 解决什么问题。能判断一个功能需不需要 RAG，以及 RAG 出问题时该从哪几个环节排查。

### 学习资料

> [!info] 看这些就够 · 约 1h
> - [ ] **MCP 官网 Overview**（只看概览页，5 分钟）
>   - [打开网页](https://modelcontextprotocol.io)
>   - 核心：一个让 Agent 连接外部工具和数据的标准协议，相当于给 Agent 和工具之间定了一套"插头标准"
> - [ ] **RAG 概念**：搜一个 10 分钟的 YouTube 讲解（搜 "RAG explained"）
>   - 核心流程：Retrieval（向量搜索找相关段落）→ Augmented（塞进 context）→ Generation（模型基于检索内容回答）
> - [ ] **Anthropic — Context Engineering**（如有官方博客）
>   - 核心：给 Agent 什么信息、什么时候给、怎么压缩

### 动手练习

> [!example] 选一个跑通 · 约 30min
> - [ ] 用 **Dify** 搭一个 RAG 知识库问答：上传 2-3 份文档 → 对话 → 观察它从哪个文档段落检索出来的
> - [ ] 用 **Coze** 搭一个带工具调用的 Bot：让它能调搜索工具 → 回答
> - [ ] 用 **Claude Code** 感受 MCP 的实际工作方式（就是你现在用的这个工具）

### 术语卡

> [!quote] 搞懂这 5 个词
> | 概念 | 一句话解释 |
> | --- | --- |
> | Tool / Function Calling | 模型决定"我需要调某个函数"，应用去执行，把结果还给模型 |
> | MCP | Model Context Protocol，让 Agent 连接外部工具/数据的标准协议 |
> | RAG | Retrieval-Augmented Generation，先搜索再回答，减少幻觉 |
> | Memory | Agent 的记忆能力：短期（当前对话）和长期（跨对话持久化） |
> | Context Engineering | 精心设计给模型的输入信息，让它做出更好的决策 |

### 快速验收

> [!question]- 题目 · 点击展开
> 你们的知识库问答 Agent 上线后，用户反馈"文档里明明写了，但 AI 说没找到"。
> 从 RAG 的流程角度，可能是哪几个环节出了问题？（至少说出 3 个）

> [!success]- 参考答案 · 点击展开
> 1. **切片问题** — 关键信息被切在两个段落之间，检索只拿到一半
> 2. **检索失败** — 向量相似度没匹配上，相关内容没进 Top-K 结果
> 3. **Context 截断** — 检索到了但拼进 prompt 时超出 context window 被截掉
> 4. **模型忽略** — 检索到了也在 prompt 里，但模型没用上，自己编了答案
>
> RAG 是一条流水线，每一段都可能断。这就是为什么 RAG 问题排查需要逐段检查。

> [!warning] 常见坑
> - **别一上来就怪模型。** 这类反馈有七八成不是模型问题，而是切片和检索的问题，先查流水线再查模型。
> - **"加个 RAG"不是万能药。** 如果知识库本身陈旧、冲突、无结构，RAG 只会更快地给出错误答案。

## 第4周 · 体验 Agent 产品，建立设计直觉

> [!tip] 本周目标
> 通过体验和拆解现有 AI 产品，建立对"好的 Agent 体验"的直觉。能说出一个 AI 产品的体验好在哪、差在哪，以及为什么。

### 体验产品

> [!info] 深度体验选 2 个，每个至少用 15 分钟完成一个真实任务 · 约 1.5h
> - [ ] **Perplexity** — 观察它怎么展示搜索过程、引用来源、追问建议
> - [ ] **Cursor / Claude Code** — 观察它怎么处理多步任务、出错时怎么恢复
> - [ ] **Google Gemini Deep Research** — 观察它的研究过程展示、报告生成、信息透明度

> [!tip] 带着这 4 个问题去体验
> - 用户能看到 Agent 在做什么吗？（透明度）
> - 出错了怎么告诉用户？用户能干预吗？（控制感）
> - 等待过程是什么体验？有进度反馈吗？（等待设计）
> - 结果怎么呈现？有引用来源吗？（可信度）

### 动手练习

> [!example] 选做 · 约 1h
> - [ ] 用 **Dify / Coze** 搭一个多步骤 Workflow：用户提问 → 搜索 → 整理 → 回答
> - [ ] 打开每个节点，看输入和输出，理解数据怎么在节点之间流转
> - [ ] 故意给一个边界 case（空输入、超长文本），观察出错时用户看到什么

> [!note] 提醒
> 写代码搭 Agent 是选修项，不是必须的。产品的核心能力是评价和设计，不是实现。

### AI 产品 UX 核心模式

> [!quote] 体验完产品后，总结你观察到的设计模式
> | 设计模式 | 解决什么问题 | 好的做法 |
> | --- | --- | --- |
> | 过程透明 | 用户不知道 Agent 在干什么 | 展示步骤（"正在搜索 → 正在阅读 → 正在整理"） |
> | 渐进式结果 | 等待时间长，用户焦虑 | 流式输出，边生成边展示，而非等全部完成 |
> | 来源引用 | 用户不知道结果能不能信 | 每条结论标注来自哪篇文献/哪个段落 |
> | 用户控制 | Agent 跑偏了用户没法干预 | 关键节点让用户确认，允许中途调整方向 |
> | 错误恢复 | 出错了用户不知道怎么办 | 区分错误类型，给出具体的下一步建议 |

### 快速验收

> [!question]- 题目 · 点击展开
> 你们的 AI 搜索功能上线后，用户反馈"不知道 AI 在干什么，等了 30 秒突然蹦出一大段文字，不知道能不能信"。
> 从产品角度，你会怎么改进？

> [!success]- 参考答案 · 点击展开
> 三个方向：
> 1. **过程透明** — 展示执行步骤（"正在搜索相关文献 → 正在阅读 3 篇论文 → 正在整理结论"），让用户知道它在做什么
> 2. **结果可信** — 每条结论标注来源（来自哪篇文献的哪个段落），用户可以点击验证
> 3. **用户控制** — 允许中途调整方向（"换个角度搜索"），或在关键节点让用户确认再继续
>
> **本质：Agent 不是黑盒。** 好的 AI 产品让用户感觉"我在指挥一个助手"而不是"我在等一个魔法"。

> [!warning] 常见坑
> - **透明不等于把 chain-of-thought 全倒给用户。** 展示"在做什么"（步骤），不是"在想什么"（原始推理），后者既烧 token 又增加认知负担。
> - **别把进度条做成假的。** 无法预估进度时用步骤反馈代替百分比，假的进度条比没有更伤信任。

## 第5-6周 · Eval + 产品落地

> [!tip] 本周目标
> 能判断一个 Agent 功能好不好，不是凭感觉，而是用 Eval 数据说话。能把前面学的东西落进你实际负责的产品场景。

### 学习资料

> [!info] 理解 Agent 评测 · 约 1h
> - [ ] **Anthropic — Demystifying evals for AI agents**（博客，不是论文）
>   - [打开文章](https://www.anthropic.com/engineering/evaluating-ai-agents)
>   - 核心：Agent 评测要覆盖三层——单步行为（工具调对了吗）/ 轨迹（过程合理吗）/ 最终结果（用户满意吗）

### 动手练习

> [!example] 结合你的实际工作 · 约 2h
> - [ ] 拿科研助手的一个**真实失败 case**，从产品视角拆解：
>   - 用户看到了什么？体验在哪一步崩的？
>   - 根本原因是技术问题（工具/检索/模型）还是设计问题（流程/交互/提示）？
>   - 如果要防止这类问题，产品层面该怎么设计兜底？
> - [ ] 尝试为一个功能定义"好"的标准：
>   - 用户维度：任务完成了吗？结果可信吗？等待可接受吗？
>   - 业务维度：成本合理吗？调用量健康吗？
>   - 写出 5 条以上测试用例 + 期望结果 + 评分标准

### 怎么写 AI 功能的产品需求

> [!todo] 上了这几周课，回头看你写的 PRD，检查这 4 件事
> - [ ] 你的需求文档里有没有写清楚"该用 Workflow 还是 Agent"？
> - [ ] 有没有定义 Agent 出错时的用户体验？（不只是"显示错误提示"）
> - [ ] 有没有定义评测标准？（而不只是"体验好"）
> - [ ] 有没有定义透明度要求？（用户能看到 Agent 的哪些中间过程？）

### 术语卡

> [!quote] 搞懂这 5 个词
> | 概念 | 一句话解释 |
> | --- | --- |
> | Agent Eval | 评测 Agent 整体表现，不只看最终答案，还看过程 |
> | Task Success | 任务是否完成了用户的真实意图 |
> | Groundedness | 回答是否有依据，而不是编造的 |
> | LLM-as-a-Judge | 用另一个模型来打分评测 |
> | Eval Set | 一组测试用例 + 期望结果 + 评分规则 |

### 快速验收

> [!question]- 题目 · 点击展开
> 你的科研 Agent 上线后 Task Success Rate 是 65%，低于目标 85%。
> **下一步最该做什么？**

> [!success]- 参考答案 · 点击展开
> **先分类失败，再对症下药：**
> 1. 拉出失败 case 的 Trace，人工看 10-20 条
> 2. 按失败原因分类：工具调用失败占 X%、理解错误占 X%、检索失败占 X%、幻觉占 X%
> 3. 优先修占比最高的那类，不要同时改多处
> 4. 修完重跑 Eval，确认指标提升且没引入新问题
>
> **常见错误：** 看到低分就直接改 prompt，不知道原因就乱改，A 问题修了 B 问题反而变差了。

> [!warning] 常见坑
> - **别只看一个总分。** 65% 是一个"平均分"，真正有用的是失败原因的分布图——它才告诉你该改哪。
> - **别只看离线 Eval。** 上线后还要看真实用户行为：放弃率、追问率、人工接管率，这些往往比 Task Success 更早暴露问题。
> - **成本也是指标。** 一个 95% 成功率但单次调用 5 块钱的功能，业务上可能是失败的。
